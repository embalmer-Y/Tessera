# HLD · 合同泛化与资源分级（通用域解放 · 合同泛化批）v0.1

> **状态**：v0.1（2026-10-13，DEC-56/57 · Q-39/Q-41 全 A 后的深度设计）。**门④**：§2.4/§3.4/§4.3 的安全合同措辞提案须 owner 批准后才可进 LLD 修订。
> **输入**：DEC-56（standalone 一级模式/复杂度不限/形态不限）、DEC-57（Q-39 资源五项 + Q-41 仲裁四项全 A）、R7（工程链/WAMR 事实/档位先例）、R8（工业先例：EtherCAT 按通道替代值/ISO 17757/EN 60204-1 §9.2.3-9.2.4/ISO 13850）。
> **范围**：固件框架的部署模式、控制源仲裁、estop 清除通道、资源档位、设备能力发现与安装匹配、资源外置打包。不涉及 Agent 侧（HLD-agent v0.2）与信任链（生态批）。

## 1. 总原则

1. **合同本体不削弱**：十条合同的既有语义对 orchestrated 设备**一字不变**；泛化 = 新增模式条目 + 既有条目的模式化限定表述。
2. **显式声明、不学习**（合同 10）：模式/档位/能力全部为构建期或部署期（prov）声明，运行时不推断不自修改。
3. **数值走实测**：large 档的具体数值（尺寸/内存/槽）由 Agent 批 AG7 实测数据补呈（Q-39 既定），本文定结构与机制。

## 2. 部署模式（Q-41①）

### 2.1 模式定义

| 模式 | 编排通道失联时 | 适用 |
|---|---|---|
| `orchestrated` | **现行为不变**：linkmon 心跳丢失（DEC-22 参数）→ 全输出进 SAFE_LINKLOSS | 被编排端点（机械执行器等） |
| `standalone` | 断链 = **事件留痕（TS_EVT_LINK_LOSS 既有事件面），不触发状态迁移**；本地逻辑照常 | 独立使用设备（本地温控器等） |

两模式下**本地合同全量生效**：三安全态/唯一写路径/限幅/看门狗四层/estop 硬件至高——standalone ≠ 无安全，只是失联语义不同（ISO 17757「自治机器须在任何通信失效下维持安全运行」背书）。

### 2.2 声明位置与迁移

- **prov 增 `deploy_mode` 字段**（CBOR schema v2——DEC-30⑤ schema 演进，向后兼容：缺省 = orchestrated，fail-safe 侧）。
- 运行时切换：**V1 不做**（构建期/provisioning 期定；重配 = 重新 provision——显式、可审计）。运行时动态切换（本地 UI 切模式）随本地交互设备的实际形态按需立 Q。
- 混合形态（按通道组声明）：**V1 不做**，机制上 prov schema 预留数组形态余地，需求实证后启用。

### 2.3 linkmon 绑定

linkmon（LLD-ts-net §linkmon）的断链→safety 迁移调用增加模式守卫：`deploy_mode == orchestrated` 才迁移；standalone 下 linkmon 仍产事件（观测不变），不调迁移。**恢复语义对称**：orchestrated 恢复 = 现行显式重写（DR-04）；standalone 无迁移故无恢复动作。

### 2.4 合同措辞提案（门④——原文呈 owner）

> **合同 3 修订案**：「**被编排的设备**：宿主/网络失联 → 输出进安全态（断链 fail-safe）；**独立运行的设备**：编排通道失联为留痕事件，不改变输出控制权；输入流不因保护而中断（两种模式相同）。部署模式由 provisioning 显式声明，运行时不推断。」

（原合同 3 文字「宿主/网络失联 → 输出进安全态」保留为 orchestrated 模式的定义句；新增模式限定句。）

## 3. 控制源仲裁（Q-41②）

### 3.1 席位模型

仲裁主体集合 = **{ zenoh 命令（租约持有者）, 本地交互源 }**；estop = 席外至高（合同 5 不动）。本地交互源 = 设备本地交互外设（形态不限——触摸/按键/未来任何本地输入），其存在性 = 设备外设事实（DT/prov 声明），无则该席位空缺（现全部板卡如此——**零行为变化**）。

### 3.2 压制机制（本地优先）

- 本地源**激活期**（本地交互会话进行中——具体信号由本地输入驱动定义，如按键按下/UI 会话打开）：写类命令（sys 面写命令 + natives 写路径的**编排来源**请求）拒绝并回执 `TS_E_STATE`（detail: local_active）——EN 60204-1 §9.2.4「激活站独占引发权」同型。
- 机制落点：safety 层新增**控制权状态**（`arb_owner: remote | local`）——单一布尔状态 + 审计迁移事件（TS_EVT_ARB_* 新事件类，kind 注册表登记）；租约模型（DEC-41）联动：本地激活 = 租约强制失效视图（远程 acquire 回执降级提示），本地释放 = 远程可重新 acquire。
- **切换零输出原则**（EN 60204-1 §9.2.3 同型）：arb_owner 迁移本身不产生任何通道写入——只改门控位；输出连续性由 APP 逻辑承载（Q-41④ 简化裁决）。

### 3.3 审计归因

既有审计 actor 字段（IR-08 修复后 app_id 归因）扩展来源维度：`src: zenoh | local`——每次写路径留痕含控制源（回溯「谁在什么时候压着谁写了什么」）。

### 3.4 合同措辞提案（门④——原文呈 owner）

> **新增合同 11（控制源仲裁）**：「设备可接受远程编排与本地交互两类控制源。本地交互源激活期间，远程写命令被拒绝；控制权切换本身不产生输出，且全程留痕。estop 硬件通道高于一切控制源（合同 5 不受本条影响）。」

## 4. estop 清除通道（Q-41③）

### 4.1 按设备能力声明

| 设备能力 | estop 清除通道 |
|---|---|
| 无本地交互（现全部板卡） | **维持现状**：远程 estop-clear（confirm="estop" 硬令牌）——无本地手段可用，令牌 = 补偿控制；**对 ISO 13850 的有据偏离，登记于 LLD-ts-safety 已知限制节** |
| 有本地交互 | **本地清除为主**（estop 器件物理脱开 = ISO 13850 语义）；远程清除可配置（prov：`estop_remote_clear: enabled | disabled`，缺省 disabled——保守侧） |

**触发面永不动**：estop 硬件 ISR 直达、锁存、事后补发（合同 5 + estopbench 实证语义）双模式一字不差。

### 4.2 措辞提案（门④——原文呈 owner）

> **合同 5 附注增补**：「estop 之清除：具备本地交互能力的设备以本地清除为主（远程清除可由 provisioning 禁用）；无本地交互能力的设备允许远程清除但须硬令牌确认。清除不解除锁存条件外任何状态、不引发输出（既有语义）。」

## 5. 资源档位（Q-39②④⑤）

### 5.1 档位结构

- manifest v2 增 `tier: "small" | "large"` 字段（缺省 small——向后兼容）+ large 附资源声明（`needs: {linear_memory_kb, stack_kb, resources[]}`）。
- **门分档**（Q-39⑤：门不撤只分档）：small 维持 16KB；large 档数值 = AG7 实测补呈（结构先定：`TS_APP_SIZE_GATE_LARGE` Kconfig，板级可配——异构设备资源不同的承载点）。
- **内存钉死**（Q-39④）：manifest needs → 编译期 `-Wl,--initial-memory/--max-memory/-z stack-size`（三方一致纪律）；固件装载校验 manifest 声明 ≤ 设备档位上限，超 = 拒装（安装期，非运行期 OOM）。
- fast interp 2× 预编译码代价（R7）计入 large 档内存账；**AOT 复评钩子**：AG7 实测若 large 档解释执行性能不达（判据：UI 类 APP tick 预算超限），提 AOT 构建选项呈递（DEC-25 既定预留）。

### 5.2 设备能力发现与安装匹配（异构设备生态基础）

- `sys/get-info` 响应增 `caps` 块：`{tiers: ["small","large"], peripherals: [...], max_linear_memory_kb, slot_pool_kb}`——**设备自报档位**（Android getMemoryClass 同型）。
- 安装期匹配矩阵（appmgr install 链新增步骤，位于验签后、槽写入前）：tier 支持否 / linear_memory 预算够否 / 资源清单可满足否（fs_paths 前缀存在于设备 fs 否）——任一不满足 = 拒装（TS_E_RANGE + detail 指明缺口），回执结构化呈报。

### 5.3 槽池与装载缓冲分级

- 槽池（store v2 槽池）按档位分区或统一大槽（**结构决定**：统一大槽 + 档位逻辑上限——实现简且不碎片化存储；具体随 LLD-ts-store 修订定，倾向统一大槽）。
- `TS_APP_LOAD_MAX` 装载缓冲：large 档要求缓冲 ≥ large 尺寸门——板级配置联动（native_sim CI 维持 small 档运行，板级按板声明）。

## 6. 资源外置打包（Q-39③ 带出的新设计题）

**问题**：TSAP = 单 wasm 容器（DEC-21 不变）；大资源（字体/点阵/表）外置 ts-fs 后，**资源如何随包分发到设备**。

**方案 A（建议）——部署会话资源推送**：Agent 部署链（A06/app_deploy）扩展：package 后扫描 project.json 资源清单 → 部署会话分两步：①装 TSAP（既有链）②经 ts_fs 写入通道推送资源文件到 `fs_paths` 白名单目录（manifest 资源声明与 fs_paths 联动 = 三方一致的新增面）。设备侧无格式变更；资源完整性 = sha256 随安装审计。
**方案 B（备选）——TSAP 容器 v3 多段**：容器加资源段。代价：格式门③级变更 + 固件解包链全改 + 验签范围扩大——**为分发便利动核心容器，违反质量优先下的最小振动原则，不建议**。
**侧载（未来生态批）**：资源文件走侧载通道时与 APP 同等验签纪律（R9 教训：任意介质先验签后接受）。
