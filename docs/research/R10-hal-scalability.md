# R10 · HAL 扩展性与安全边界（owner 架构讨论留档）——平台长期架构在案依据

> **日期**：2026-10-16 · **触发**：owner 2026-10-16 架构问询（「APP 全量 AI 开发确认 + HAL 意义 + 硬件适配膨胀 + 直接暴露 Zephyr API 可行性」）· **消费方**：未来 HAL 扩展裁决（门③）与长尾硬件接入方案选型。
> **方法**：owner 会话讨论 + 本地事实（AGENTS §6 合同 / LLD / impl-review-02 正面实证 / F6 根治记录）+ 业界同型对照（WASI / WebUSB / Android HAL / seL4——来源见 §6，无新 web 实抓，同型机制为公知设计模式）。
> **结论先行**：①「APP 全量 AI 开发」与 HAL **互为条件而非竞争**——HAL 是 AI 生成代码的目标合同面（窄面 = 收敛可靠性）+ 不可信代码的安全边界；② 直接暴露 Zephyr API **八问题逐条否决**（且绑定层工作量逃不掉，并不省事）；③ HAL 膨胀威胁的是**维护成本**而非安全——安全边界 O(1)（唯一写路径 / caps 绑定 / chokepoint natives 三道咽喉不随类数增长）；④ 长尾硬件正解 = **特权驱动组件**（经人审签名信任层，对普通 APP 只暴露 msg/fs/av 既有通道）+ **通用动词 + 设备级策略数据**（安全决策从 API 代码移到策略数据）——两者都不放宽沙箱；⑤ 前置件恰为 P1-1（ts_msg_send，特权组件对外服务的载体）。

## 1. 前提确认：APP 功能全量由 AI Agent 开发

既定裁决链落点（DEC-12 v1.1 双角色 / DEC-56 通用域解放 / Agent 批 AG1-AG8 创作循环）。仓内事实：D1-D9、NVD、AG7、AK 系列 demo 的 APP 代码**全部真 LLM 生成**；人手写 C 仅框架本体与 bench 载体。此前提为现状，非待办。

## 2. 直接暴露 Zephyr API 的问题清单（逐条否决）

技术前提：Zephyr API 为 C 接口（裸指针/内核对象/栈上下文），与 WASM 线性内存无天然调用通路——「直接暴露」实为「生成巨大绑定层」，工作量不省而问题全保留：

| # | 问题 | 机制 |
|---|---|---|
| 1 | 权限模型不存在 | Zephyr API 无调用者概念；`device_get_binding` 无 caller 上下文——按 manifest caps 裁决须逐 API 事后包拦截层 = 重造 HAL 且更差 |
| 2 | 安全合同全线失效 | 合同 2 唯一写路径（L5 机械检查）是安全根；APP 直调 gpio/pwm 后 estop 无法强制安全值（管脚所有权在 APP）、断链 fail-safe / 限幅 / slew 无插足点 |
| 3 | 确定性与重放破坏 | 合同 9 依赖有界可记录系统调用面；k_thread/ISR 注册/异步回调使 DEC-31 单线程模型与 sim↔real 逐行对拍（NV-3）不可能 |
| 4 | 资源计量失守 | 内存账 = APP 线性内存即预算；k_malloc 走系统堆可榨干框架自身；指令配额按回调入口计账，APP 自建线程后喂狗/配额模型全失效（F6 = 优先级问题即楔死整板的实证） |
| 5 | API 面爆炸 | Zephyr 公共 API 数千符号；四道确定性门（编译→白名单面检查→尺寸→双编译一致）建立在 natives 十几个之上；AG7「imports 恰等于白名单子集」的收敛性消失 |
| 6 | 板耦合回归 | API 行为依赖 DT（v4.4 EDT 宏发射坑实证）；APP 编译期绑定具体板 → DEC-04 板无关 / caps 装前预检 / 跨板复用作废；Zephyr 升级破坏已部署 APP |
| 7 | 网络隔离消失 | 裸 socket 绕过 zenoh 命名空间 / 租约 gated 纪律 / QoS 映射 |
| 8 | 审计咽喉没了 | 每个 ts_* native 是审计/限速/分账 chokepoint；直调后「谁何时对哪个通道做了什么」结构上不可回答 |

根因一句话：Zephyr API 的前提是「调用者 = 开发者本人」（可信、编译期固定）；我们场景的前提是「调用者 = 不可信的 AI 产物」——两者相反。业界无平台走此路：**WASI 自身否决裸 POSIX passthrough 改为能力作用域语义函数集**（与 natives 同型）。

## 3. 重新框定：膨胀威胁的是维护成本，不是安全

**安全边界 O(1)，不随能力类数增长**：

1. 唯一写路径 `ts_safety_commit`——所有类、所有执行器同一扇门（L5 机械检查在案）；
2. 实例化期 manifest caps 绑定——WAMR 导入子集注册（合同 10 机械能力边界）；
3. chokepoint natives——审计/计量/分账单一咽喉。

加 `ts_av_write` 未增加任何新逃逸路径——同一堵墙内多开一扇窗。HAL 增长的真实代价 = 每类设计与评审成本（native + 权限类 + manifest + Agent 镜像 + L5 + 测试）+ 长尾接入速度。**增长率注**：类数 ≈ 语义能力类数（gpio/pwm/adc/log/kv/fs/av/msg/power ≈ 十个）而非芯片数——`ts_pwm_set` 罩住所有 PWM 芯片，具体芯片驱动是 HAL 之下的板级胶水（hal_espressif）。会痛的是**长尾**（冷门协议芯片/专用执行器/总线设备）。

## 4. 解法（分层：已内置 → 长尾演进 → 治理）

**已内置的两个控制项**（当前设计自带刹车）：

- **需求门控增长**：每类入菜单须真实 demo 消费者 + 门③裁决（av/fs 走 Q-27、档位走 Q-39）；无投机性泛化；P1-4 counter 大概率裁撤 = 纪律在工作。膨胀真源 = 投机性 API，不是需求驱动类。
- **外设描述符注册表（ts-periph）**：新外设实例走数据（DT overlay + uid/kind/安全参数）非代码（periphbench → F4 自报同路）；同类第 N 个芯片零框架改动。

**长尾解法 A：特权驱动组件**（微内核 seL4 / Android vendor HAL 同型）——冷门硬件驱动做成**单独签名特权组件**：走与固件同套人审/签名信任链（TSAP + 信任根表现成），对普通 AI APP 只经**既有通道**（msg/fs/av）暴露窄服务面。HAL 保持十几个类，危险面保持有界（特权层人审、AI 层照旧全沙箱）。**前置件 = P1-1 ts_msg_send**（特权组件对外服务载体）。

**长尾解法 B：通用动词 + 设备级策略数据**（WebUSB/WebSerial 同型）——总线类长尾提供少数**语义成形**通用动词（如 i2c 事务/帧流），安全决策在策略数据（DT/manifest 声明「哪个 APP 可访问哪个设备地址 + 速率上限」，框架做 allowlist + 限速 + 审计）。扩展新设备 = 写策略零框架代码。仍非裸暴露：动词有完整边界与计量，策略是声明的。

**治理**：类集合每版本批复审「该类是否仍有消费者」，无则日落（counter 为第一候选）；类集合设冻结点意识（核心十类之外新增须门③）。

## 5. 业界同型对照（公知模式，非本轮实抓）

| 平台 | 做法 | 与本文对应 |
|---|---|---|
| WASI | 否决裸 POSIX；能力作用域语义函数集 | natives 形态同型（§2 根因） |
| WebUSB/WebSerial | 不暴露 OS USB API；成形通用动词 + 站点级权限授予 | 解法 B 同型 |
| Android | HAL 按类 curated；vendor HAL = 独立构建签名的特权组件，app 只见 manager API | 解法 A 同型 |
| seL4/微内核 | 驱动 = 用户态服务 + capability 令牌；小 TCB 是可证明安全的前提 | 「可信核心保持小」同型 |
| ROS2 | 硬件驱动 = 节点，经 topic/service 暴露 | 解法 A 的上层形态 |

## 6. 对当前计划的落点

- P1-1（ts_msg_send）从「多 APP 业务最后一环」升级为「解法 A 的地基」——优先级不变，动机登记增强。
- 本文档为未来 HAL 扩展门③呈递的在案依据：新类默认走需求门控；长尾默认走 A/B 而非扩 natives；「直接暴露 Zephyr/宿主 API」类提案以 §2 清单直接否决。
- 与 DEC-33 北极星一致：能力类增长压力的终极出口是 DomainPack/域插件层（框架核心十类冻结，域语义在域包内自定）。
